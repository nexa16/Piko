# Owner AI service

Local implementation; deployment is separate. Both `PIKO_AI_ENABLED` server environment and private SQL config default off; the initial allowance and pricing are zero. No public AI access is granted by anonymous sign-in. The app's public project URL/publishable key and function URL are build configuration; provider and service-role secrets belong only in the server secret store. Never place secrets in Dart defines or committed files.

Run `npm ci --ignore-scripts` and `npm test` here. Tests use pinned PGlite PostgreSQL and fetch fixtures, with no paid or hosted calls. This proves local SQL behavior and protocol cases, not hosted concurrency, deployment, Auth settings or language quality. `index.ts` pins the server SDK and verifies an anonymous user through `getUser(jwt)` before the privileged allowlist RPC. Platform JWT verification stays enabled.

Before activation, review a dedicated project and its region, current free-tier limits, current model prices/conversion, a numeric allowance and conservative per-request reservation. Apply the migration through the Supabase CLI after authorization. Set an expiring enabled owner UUID in `piko_ai_private.owner_access`; never trust user metadata. Configure the current UTC active month, price snapshots, reservation, allowance and concurrency together under the config-row lock. Do not reset accumulated spend within the same month. Unknown outcomes keep their reservation. No automatic allowance refill or monthly reset is installed.

The function starts one background Responses attempt and polls its owned response ID. No retries or second judge. Results remain proposals; structured output is not semantic validation. Prompts/results are not stored in Piko SQL or application logs. Background processing temporarily retains responses at OpenAI for about ten minutes, including with `store:false`; standard provider processing also applies. See [OpenAI background processing](https://developers.openai.com/api/docs/guides/background).

Install database-owner scheduled maintenance only after reviewing the dedicated-project assumption: daily `select public.piko_ai_cleanup();` followed by `select piko_ai_private.purge_inactive_anonymous_identities();`. The first removes receipt metadata older than 35 days and inactive access rows after 90 days, without refunding balances. The second deletes only anonymous Auth identities inactive for 90 days without recent AI activity/receipts, including their sessions; it is revoked from app and service roles. Confirm the actual job and retention behavior before claiming retention is active. It must not run in a shared unrelated Auth project.

Before live use, inspect hosted security/performance advisors, RLS and RPC grants; test two real concurrent connections against atomic admission, owner expiry/replay/quota paths, platform JWT verification, anonymous signup rate settings and session refresh. Review signup abuse protection separately before broader access. Run action-specific live quality evaluations only with a separately authorized budget. No hosting, deployment, paid evaluation or broader rollout is implied by this implementation.
