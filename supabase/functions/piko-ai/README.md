# Private AI test service

Local implementation; deployment and activation are separate. App/server build gates and SQL admission default off. Public project configuration never grants access; provider/service-role secrets stay exclusively in the server secret store. Missing configuration fails closed.

Run `npm ci --ignore-scripts` and `npm test` here. Pinned PGlite tests exercise both the preserved first migration and the r2 pilot migration; fetch fixtures never make paid calls. Queued simultaneous PGlite requests exercise atomic statements, but do not establish hosted multi-connection behavior. `index.ts` pins its SDK and verifies anonymous Auth using `getUser(jwt)` plus a matching live `auth.sessions` row from the verified token. Missing, revoked or expired sessions fail closed; user metadata grants no permission. The session-check migration grants the server role only the three required Auth columns, with no app-role RPC access.

## Admission and activation

Use a dedicated, separately approved project. Apply the admission, private-pilot, session-check and cleanup migrations in order. The declared Auth configuration enables optional anonymous sessions, short access-token lifetimes and bounded enrollment; it does not invite an identity or enable paid dispatch. The second disables the prior owner-only configuration. Provision fixed nonreusable invitation slots 0–5 (0 for the owner), one Auth UUID per slot, with individual expiry/revocation; never grant slots through a client API or recycle them during the pilot. Verify identity recovery manually before any later pilot instead of silently rotating allowance.

The config stores one start/end interval of exactly 14 days, reviewed maximum all-in input/output prices and conversion, conservative per-request reserve, shared usage allowance, non-AI usage, available prepaid balance and new cash outlay separately. The configured caps are checked without double-counting purchase and usage. No monthly reset, renewal, top-up or paid fallback exists. Do not reset the reserved/spent counter. Admitted failed/uncertain attempts count. The review-job migration separates expiring dispatch leases from retained uncertain cost reservations: expiry/cancellation never refunds an unknown attempt or authorizes replay. Secondary limits remain 20/identity/UTC-day, two/minute, one in flight; all identities share the global balance. Provider processing is fixed Sol low with strict schema, no tools/second judge, background processing and `store:false`. One POST is one attempt; owned GETs poll that response or return its already captured private result without a provider call.

## Durable Collection review

`20261023120000_review_jobs.sql` adds private jobs, uploaded chunks, steps and cancellation tombstones. It does not enable paid review or install a worker cron job. All tables enable RLS and deny app roles; only the authenticated service adapter can invoke the narrowly granted RPCs. The worker is a separate endpoint with its own random secret, no app JWT path and a disabled function configuration. Set neither environment gates nor SQL `review_jobs_enabled` before separate reviewed deployment/activation.

The JWT-protected `piko-ai` endpoint accepts `?job=prepare|upload|start|resume|cancel` by POST and `?job=status|result&jobId=<UUID>` by GET. Every POST includes `jobId`. Preparation binds installation/idempotency identifiers, frozen sorted `scopeIds`, collection/languages/options/category definitions, snapshot version/digest, explicit `maxCostCents` and the client's fixed `expiresAt`. Content chunks contain at most 50 entries and are immutable by index. Canonical SHA256 uses UTF-8 JSON with recursively sorted object keys, sorted entries/groups/values/assignment values, and preserved example order. The manifest has `version`, `collection`, `options` (including filters), `entries`, `groups`, `allowNewGroups`, `allowNewValues`; it excludes learning/history/device data. Start recomputes the complete digest and validates every scoped ID before constructing a finite plan. No excluded vocabulary is used as context.

Status contains `jobId`, `snapshotDigest`, `snapshotVersion`, `state`, monotonic `generation`, `expiresAt`, `processed`, `total`, `phase`, cost counters and `resultAvailable`. States are preparing/running/paused/unknown/completed/failed/cancelling/cancelled/expired. Known limit details include cause, numeric bounds/unit and a known retry instant; unavailable details are not guessed. Completed results use the ordinary review envelope with original saved UUIDs plus job/digest and read-only conflict alternatives. Result GETs accept `part` (default zero) and return `{jobId,snapshotDigest,resultHash,part,parts,content}` with at most 200,000 UTF-16 code units per part. Concatenate immutable parts in order and verify SHA256 of the complete UTF-8 JSON text before parsing/storing; do not reserialize before hashing. Equivalent category definitions from independent steps are aliased; incompatible modes/proposals remain unresolved. Suggestions are unavailable before every detail and consistency step completes. Cancellation before a lost preparation response creates an owner-bound tombstone, preventing a delayed request from admitting work after acknowledgement. Status, retained results and cancellation remain callable while paid-dispatch gates are off, subject to owner/session/consent/retention checks.

Detail batches contain at most 50 complete entries and fit measured provider-body limits. Compact consistency shards include every admitted meaning/category, and the finite DAG compares every shard pair, so a pure sequence of independent detail batches cannot masquerade as Collection-wide checking. An oversized single entry, more than 256 steps, insufficient declared worst-case budget or a plan exceeding fixed remaining admission time is rejected before paid dispatch. Operator pricing/output configuration is frozen at start. Each dispatch reserves its own conservative maximum at the shared and job caps; settled usage is applied exactly once. Queue messages contain only a job ID. Workers claim under an atomic lease, persist a dispatch fence before POST and never replay a potentially sent request. Missing provider IDs become unknown, not new attempts. Provider polling is bounded and completed outputs are persisted independently of the short `store:false` polling window.

One confirmed start permits server processing while the app is closed. Day/budget limits pause; explicit resume continues safe remaining steps. Unknown steps require resolution/cancellation and never trigger a replacement POST. A job expires at the earliest of the client's original deadline, seven days, owner access expiry and fixed pilot end. Withdrawal deletes all job content immediately, fencing callbacks. Existing 22-day live content/30-day managed-copy target applies to snapshots/results; cancellation tombstones retain only minimal metadata for at most 35 days. Cleanup never refunds reservations or extends an original retention clock.

For a reviewed deployment, provision a separate random `PIKO_AI_REVIEW_WORKER_SECRET` as an Edge secret, and matching Vault entries `piko_ai_review_worker_secret` and `piko_ai_review_worker_url` pointing at the dedicated internal worker endpoint. After verifying extension availability, private queue/table/sequence grants, worker authentication, real concurrent connections and retention, the database owner can call `piko_ai_private.configure_review_worker(true)` to install a one-minute scheduler. `false` removes that scheduler. This operator-only function is not granted to app/service roles and is never invoked by migrations/tests. The function/environment/SQL dispatch gates all remain independent. No secrets belong in cron source, client bundles, logs or this document.

Local PGlite tests execute the actual review SQL with a minimal queue fixture because PGlite does not bundle PGMQ. They verify owner isolation, cancellation/admission races, leases, costs, retained results, withdrawal and cleanup. These fixtures do not establish hosted PGMQ semantics, Free-plan availability, live multi-connection scheduling, actual language quality, backup deletion or deployment acceptance.

Before setting `deployment_verified`, verify actual prices/tax/FX/fees, Free-plan eligibility, funding and allowance, region/processors, Auth/JWT/session/abuse controls, secure transport/storage, private schema grants, required maintenance and ALL managed-copy/backup expiry. Supply the real notice version, invitation contact and processor/storage details. Activation needs separate authorization and source-bound verification; setting a flag is not evidence that these checks passed. A stale/missing cleanup heartbeat denies new calls. Do not edit the fixed interval to renew it.

## Consent and private analysis

Generation/gap responses constrain saved-entry edits to category assignments; an empty saved inventory permits no edits. New cards carry their examples and other content directly. This request-specific schema does not impose a card quantity, alter review corrections or replace the app's independent validation.

Authenticated POST control operations use `?pilot=notice|consent|withdraw|feedback|adoption`; ordinary clients have no table/RPC grants. Consent requires the current notice version and an invited identity. Withdrawal remains available when AI dispatch is disabled, immediately revokes that identity and deletes its live payloads. Keep the endpoint/Auth path available after pilot expiry so withdrawal can finish. Admin revocation also blocks dispatch/status/logging; daily cleanup removes its content. No cross-tester payload read endpoint exists.

Accounting receipts contain only operational metadata. The separate private payload store captures the actual request/provider body, actual output (including invalid paid outcomes), refinement lineage, version information and reported adoption/optional feedback. Nothing is printed to application logs. Client adoption is reported after the local atomic commit; delivery failure means unknown adoption, never an excuse to repeat the local write. Retained context excludes learning/statistics and unrelated Collections. Regression records require explicit human de-identification review; app/server roles cannot create or read them.

## Expiry and copies

The cleanup migration installs database-owner maintenance every six hours: `select public.piko_ai_cleanup();` then `select piko_ai_private.purge_inactive_anonymous_identities();`, and runs it once initially. Verify the actual scheduler, database owner and heartbeat on the selected deployment. The cleanup service role is intentionally revoked because regression cleanup requires owner access. Raw live payloads expire after 22 days, leaving at most one day of scheduler delay and seven days for every backup/copy (30-day upper bound). Withdrawal deletes live payloads immediately; every managed copy must expire within seven days. A copy/export must retain the original expiry, never restart its clock. Restores must apply revocations/deletion requests and cleanup before service activation. Do not enable managed backups/PITR or external exports that violate these bounds. Verify deletion across an actual backup/restore before activation; SQL alone does not prove it. Cleanup heartbeat is a fail-closed admission guard, not a substitute for a running job and operational monitoring after service shutdown.

Reviewed de-identified regressions expire after at most 82 live days and no later than pilot-end plus 82 days, preserving the same one-day maintenance/seven-day copy margin inside 90 days. Keep identities/raw quotes out of these rows. Receipt metadata expires after 35 days; inactive anonymous Auth identities/sessions after 90 days without recent activity. Unknown cost reservations are not refunded by deletion. This dedicated-project cleanup must not run against unrelated users/projects.

Provider retention is separate: background responses may remain approximately ten minutes even with `store:false`, and standard processing applies. See [OpenAI background processing](https://developers.openai.com/api/docs/guides/background). No zero-retention promise or provider-wide log deletion is made.

Before live use run hosted advisors, role/isolation tests, two real concurrent connections at the shared cap, expiry/replay/withdrawal races, session refresh, deletion across copies and revision-specific Android managed-provider flows. Local fixtures are not live language-quality or hosted-retention acceptance. No deployment, purchase, invitation, distribution or publication is performed by these files.
