# Maintaining the current documentation

The [build manifest](build-manifest.json) selects one APK/source baseline. The [guide](features.md) owns tasks/glossary, [technical reference](technical.md) owns implementation rules, [gallery](screenshots.md) owns image presentation and [developer setup](development.md) owns commands. Update those owners rather than copying full explanations into README or a second registry.

1. **Select an immutable candidate.** Verify APK checksum, normal package/activity, version fields, signing classification and original source/configuration. Preserve any build-affecting local patch with its digest privately and disclose that condition. Documentation commits can differ from the APK source. Do not infer identity from a branch or filename.
2. **Inspect the affected implementation.** Compare accepted work with actual selected source and product flows. Describe partial delivery only to its implemented extent. Record discrepancies, unsupported variants and verification gaps; do not fix app behavior under documentation authorization.
3. **Update the single owners.** Keep existing task anchors stable. Put practical limitations beside tasks, implementation detail in the reference and commands in setup. Use actual selected-catalog EN/DE labels. Keep plans, account notes and history out of current-app prose.
4. **Capture changed product states.** Use the selected ordinary APK, normal entry point and synthetic content on a safe emulator/device. Preserve user data. Inspect each capture, retain the original privately, and record build/fixture/state, locale, pair, dimensions, scale, orientation, time and any crop/redaction. Reuse the same image in the guide and gallery. Instrumented/mockup images cannot replace product images.
5. **Update the manifest and coverage summary together.** Record checksum/dimensions/path per stable capture ID and point documentation/source evidence to the selected baseline. Older reused images keep their actual original build and explicit justification. Never silently relabel them. Unknown required provenance prevents verified completion.
6. **Validate the bundle.** Run `node tools/check-documentation.mjs`, shared-generation checks and applicable changed-consumer tests. Exercise documented setup/build commands where available and distinguish existing-workspace checks from clean-install/platform verification. Inspect rendered Markdown at desktop and narrow reading widths; open full-size images to check labels. Technical/source claims, filenames, captions and links must agree.
7. **Review and hand off.** Record actual checks and gaps in the existing private execution ledger. Review proposed files and commit metadata for secrets, personal/identifying content, private links and machine paths. Preserve the last consistent bundle until replacement passes. Follow contribution/publication gates; no automatic push, merge or release follows documentation completion.

The checker validates structural consistency, source references, image metadata/checksums and local links/anchors. It cannot decide whether prose is truthful, a screenshot came from an ordinary APK, or a task is usable. Those require source review and direct product inspection, summarized in [verification coverage](verification.md).

Internal decisions/quick specs use the shared ignored planning store described in [AGENTS](../AGENTS.md). Never publish its contents. Retained Git history is unchanged; ignoring or untracking a file does not erase earlier public commits.
