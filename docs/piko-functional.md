## Proposed scope classification — for owner review

### Implementation-round assignment and delta process

Implementation round is an independent planning axis: 1 (accepted initial implementation), 2 (accepted second scope), 3 (accepted incremental APK checkpoints), Later (explicitly deferred), Undecided (not assigned) and Superseded. Base/Minimum/Additional are legacy scope labels, not round inclusion. The implementation ledgers record scoped test evidence, not shipped product releases. Each round filter includes new, revised and bug-fix requirements without importing unrelated later features. Publication versions, release branches and store readiness are separate decisions. Current round-3 delivery evidence is in [implementation-round-3.md](implementation-round-3.md).

Revision policy: keep stable IDs and the original `[Round: 1]` for previously implemented requirements. Change accepted behavior in place, increment `[Revision: N]`, and add `[Updated: 2]`; an implementation defect against an unchanged rule uses `[Fix: 2]` without a revision bump. New round-2 capabilities use `[Round: 2]`. The round-2 filter includes all three. Implementation evidence/status is separate from definition acceptance; round-1 evidence does not verify a new revision. Feature PRs list all covered spec IDs/revisions and tests; they squash into one feature commit on `develop`. Historical wording lives in Git and dated decisions, not contradictory active rules.

Scope labels organize implementation priority; they do not change the requirement text, stable IDs, or existing Confirmed / Proposed / Open / Superseded status. The two existing JSON interchange IDs currently have no legacy scope label; their accepted Round 2 assignment remains authoritative. A confirmed capability may be Additional and remain a confirmed product intention without being required for the first useful version. An open decision stays open regardless of its scope label. No first-version scope, release date, or implementation milestone has been accepted through this classification.

### Flow associations

Inline `[Flow: collection]`, `[Flow: entry]`, `[Flow: review]`, and `[Flow: settings]` tags connect requirements to creating/opening Collections, manual vocabulary entry, self-assessment review, and basic settings. Multiple associations use one comma-separated tag. Tags identify a topic association, including its optional extensions and conditional constraints; they do not change scope, confirmation status, or implementation completeness. Filter Flow together with Scope: `review` includes Additional review features, while `review` + `Minimum` shows only the proposed Minimum review requirements. Shared privacy, data, and localization constraints remain applicable to every associated flow. The accepted direction for this mockup pass is the visible Minimum flow; individual open functional decisions remain open.

### Historical scope-classification proposals (not current release gates)

The following bullets record the earlier classification rationale, not open decisions for either accepted release. In particular basic Long-term without Speed, EN/DE, local-first storage, Undo and previous-grade correction were accepted for Implementation round 1.

- Undo/previous-grade correction is Additional as a capability; review-history consistency is Base if correction is offered. ENTRY-009 deletion with undo is proposed as Minimum for basic entry management.

- Labels apply to an entire requirement. The four unnumbered Future / deferred ideas below are all Additional; no new requirement IDs are created for unconfirmed ideas. The experimental parameter table belongs to the Additional developer-parameter capability, while any implemented learning algorithm still needs explicit, validated parameters.

## Piko mascot state selection — accepted, 2026-10-15

Every in-app Piko illustration is purely decorative. The rules below select only which artwork is visible; they do not give the character a function, control, action or effect on learning. Existing text, counts, buttons and state handling remain authoritative and complete without the illustration. The mascot is not an interactive assistant, notification, status indicator or source of accessible status announcements.

- **MASCOT-001 [Confirmed]:** [Scope: Additional] [Round: 2] [Revision: 1] [Implementation: Specified; mockup and app pending] [Flow: collection, review] Collection Detail has at most one contextual Piko mascot. In round 2, the only enabled pose is reading Piko (source frame 3): show it when normal Long-term review is available in at least one direction for the current Collection search/filter scope, using the same authoritative readiness and due membership as REVIEW-001 and UX-COLL-008. Two available directions still produce one mascot, not one per action. Normal review availability includes whatever regular/retry items those existing rules allow; it does not require a new learning-status classification. When normal review is unavailable, show no mascot in round 2, including a Speed-only state. If both normal review and Speed are available, round 2 still shows reading Piko because frame 6 is deferred. Loading, errors and a pending retry wait must not be treated as successful completion. Recompute the illustration with the existing action state after filters/search, entry changes and returning from learning; mascot selection must never mutate vocabulary, FSRS, retries or Speed markers. App identity is specified separately by UX-BRAND-001.

  Acceptance: one or both normal-review directions available → exactly one frame 3; normal plus Speed → exactly one frame 3; Speed only, no available learning, no filter matches, loading or failure → no contextual mascot. A retry that is not yet ready retains its waiting presentation; ready review follows the same existing availability rule. Changing filters or returning after a completed session updates the mascot together with the actions. Frames 2, 4, 5 and 6 are not activated by the round-2 implementation.

- **MASCOT-002 [Confirmed]:** [Scope: Additional] [Round: Later] [Revision: 1] [Implementation: Specification only; deferred] [Flow: collection, review] When the later Collection Detail poses are implemented, resolve the single mascot slot in this order: (1) new-vocabulary Piko, frame 6, if either direction has eligible new Speed vocabulary under SPEED-005 in the current search/filter scope; (2) otherwise reading Piko, frame 3, if normal review is available under MASCOT-001; (3) otherwise sleeping Piko, frame 5, for a genuine nothing-to-learn state with neither available normal review nor new Speed vocabulary and no pending retry obligation. The owner explicitly chose frame 6 when both normal and Speed learning are available. A normal-review count of zero alone does not imply sleep while Speed is available. Preserve UX-COLL-008's distinct empty-Collection, no-filter-results, loading, error and retry-wait states rather than turning them into an all-learned/sleeping state. Never show multiple poses, rotate through alternatives or add one mascot per learning button. This later priority does not enable frame 6 or frame 5 in round 2.

  Later acceptance matrix: normal only → 3; new Speed only → 6; both → 6; neither with a genuine nothing-to-learn state → 5; retry wait with no other available learning, empty Collection, no filter matches, loading or failure → no contextual mascot. Search/filter changes use the same scope as the visible learning actions.

- **MASCOT-003 [Confirmed]:** [Scope: Additional] [Round: Later] [Revision: 1] [Implementation: Specification only; deferred] [Flow: review] Excited Piko (frame 2) accompanies a successfully finished learning session, not an individual correct answer, voluntary Exit, interruption, failed write or initially empty/no-due launch. Normal learning uses the existing completion boundary and summary under REVIEW-003; pending reinforcement prevents completion. Speed uses the all-items-completed boundary under SPEED-008, retaining its direct return to Collection and no new Speed summary/statistics popup. This cosmetic completion feedback never changes the recorded counters, learning or completion rules. Its later Speed presentation/lifetime remains to be reviewed under UX-MASCOT-003; it must not appear alongside a second Piko on Collection Detail. No completion mascot ships in round 2.

- **MASCOT-004 [Confirmed]:** [Scope: Additional] [Round: Later] [Revision: 1] [Implementation: Specification only; deferred] [Flow: review] Star-holding Piko (frame 4) belongs to the statistics view/area on the homepage when that capability is added. It is not the session-completion mascot, a new award, an earned-achievement threshold or a replacement for real statistics. This mapping does not bring homepage statistics or any new statistical calculation into round 2.

## New and clarified functional requirements

- **VOCAB-EDIT-002 [Confirmed]:** [Scope: Minimum] [Round: 1] [Flow: collection, entry] Inline Collection Detail editing retains the vocabulary pair as it was when that editor was opened. After a change, offer Finish editing and Discard changes separately: Finish keeps valid auto-saved edits and closes; Discard restores both original values and closes, including after incomplete input. Invalid or duplicate input blocks Finish. Discard must not create a duplicate or change learning progress. Auto-save remains reversible within this open inline edit session; ENTRY-005's entry-stack behavior is unchanged.
  - The repository captures the exact stored opening pair before editing becomes available. Discard waits for accepted autosaves, restores only that existing entry's texts and comparison keys atomically, and preserves identity, ordering and both directional learning records. A failed rollback retains the snapshot and input for retry; a deleted entry is not recreated. The functional capture/rollback boundary is implemented; the separate visible Discard control is tracked by UX-COLL-012.

- **REVIEW-003 [Confirmed]:** [Scope: Minimum] [Round: 1] [Flow: review] When a review session ends, show a dismissible summary popup with the number of vocabulary items learned/completed and the number correct on the first try. Closing returns to the Collection beneath the popup; do not require a separate Back to Collection action. This does not replace existing learning-history or retry-accounting rules. The actual route now opens the immutable final per-launch counters only after captured regular work is exhausted and no retry obligation remains; no-due, voluntary Exit, pending writes, correction and failed selection do not manufacture completion. Safe summary dismissal drains/stops that exact session and returns to its Collection. One real-route completion case plus the eight English/German 320px/200% popup cases verify exact completed/first-try values, no return CTA, X/Escape/backdrop/system-Back dismissal and focus restoration. Two passing English/German Android real-runtime flows additionally reach the actual summary after regular correction and retry completion, assert exact 2 completed / 1 first-try accessible metrics, dismiss to the underlying Collection and retain the resulting state across file reopen. Broader release gates remain separate.

- **COLL-017 [Confirmed]:** [Scope: Minimum] [Round: 1] [Flow: collection] A new Collection's required name is prefilled with its selected target language in the interface language (e.g. Korean/Koreanisch). Changing target language updates that default only until the user customizes or clears it. Any explicit name edit stops automatic replacement for that draft, including retyping the original default; clearing does not re-enable it. Changing the native language never renames the draft. A locale-only change preserves draft text, selection and focus under I18N-002; a later target-language change uses the current interface language if the name is still automatic. Empty names remain invalid; multiple Collections with the same language pair or name are allowed.
- **VOCAB-TRASH-001 [Confirmed]:** [Scope: Additional] [Round: Later] [Flow: collection, entry] A future vocabulary trash/recovery area retains deleted entries for 30 days after deletion. This retention period is independent of the implementation-round-1 eight-second Undo window. Detailed recovery behavior, expiry cleanup and storage/privacy implications remain to be specified. The duration is accepted during implementation-round-2 planning; implementation and the complete implementation-round-2 scope are not authorized by this confirmation alone.

- **VOCAB-EDIT-001 [Confirmed]:** [Scope: Minimum] [Round: 1] [Flow: collection, entry] Existing vocabulary can be edited directly within its expanded Collection Detail card. Valid changes to the two required language texts save automatically; incomplete or duplicate drafts must not replace the last valid stored pair. Adding vocabulary remains a separate entry-session action.
  The standalone InlineVocabularyEditController establishes the existing-entry autosave boundary without altering ENTRY-005. Stable UUID/owner, immutable raw draft snapshots, last committed pair and revision-aware errors are separate state. One worker serializes writes and coalesces the latest waiting valid pair; later invalid input stays raw while previously accepted valid snapshots may finish without clearing its validation. Repository transactions update both texts/keys together and leave directional learning state unchanged. Current duplicate/storage failures retain raw input and last committed values, with single-flight retry; stale failures cannot overwrite newer validation. Canonical-equivalent raw spaces/decomposition remain in the buffer but are not reported as unpersisted changes after draining. Ordinary typing stays available during autosave. Disposal rejects new work and clears exposed editing state; accepted writes can drain without late notifications before caller-owned storage closes. This is controller-layer evidence only: actual inline expansion, compact fields, finish/discard and Android integration retain their own pending requirements.

- **MATCH-001 [Confirmed]:** [Scope: Base] [Round: Undecided] [Flow: review] Typed answers may be submitted empty and are then treated as an answer attempt; the learner retains final authority over the Correct/Incorrect grade.
- **MATCH-002 [Confirmed]:** [Scope: Additional] [Round: Undecided] [Flow: review] Typed answer matching detects character-level near matches and accepted language-specific orthographic variants. Similarity is a suggestion, not an automatic semantic synonym acceptance rule.
- **MATCH-003 [Confirmed]:** [Scope: Base] [Round: Undecided] [Flow: review] A different meaning or wrong synonym is not automatically accepted as correct; the learner can override the suggested grade.
- **MATCH-004 [Confirmed]:** [Scope: Additional] [Round: Undecided] [Flow: review] Submitted incorrect typed answers are retained as learning events for potential future error-pattern analysis, separately from the final learner-confirmed grade.

The opposite direction is unchanged.

- **SPEED-RESET-002 [Confirmed]:** [Scope: Additional] [Round: 2] [Revision: 1] [Implementation: App planned] [Flow: review] Successful Speed completion after at least one error initializes the studied direction as a fresh FSRS generation and removes its obsolete current retry obligation. - **UNDO-001 [Confirmed]:** [Scope: Base] [Round: 1] [Flow: review] Correcting the immediately previous grade replaces the corresponding review event and consistently recalculates its FSRS state and retry scheduling rather than creating a second review. The atomic scoped transaction reuses the regular event UUID and original UTC review instant, recalculates from the receipt's exact prior FSRS card, advances only card/scope revisions while leaving the answer ordinal unchanged, and replaces/removes/restores the current-round retry without extending its original learning-day expiry. Exact latest receipt, authoritative item/scope state and any post-answer wait-mutation chain are optimistic guards; stale, forged, concurrent or non-latest correction fails without a partial write. Twenty-seven real-SQLite cases cover all 3×3 regular and retry rating transitions, wait chains, expiry, rollback/retry, concurrency and unrelated-scope preservation. Two passing Android real-runtime flows additionally replace Hard with Good using the same event UUID/original UTC instant in opposite directions and retain the corrected state across file reopen; the exhaustive transition matrix remains host evidence. Broader release gates remain separate.
- **EXAMPLE-005 [Confirmed]:** [Scope: Additional] [Round: Undecided] [Flow: entry, review] All Example Pairs of an Entry remain available on its Learning Card, including when there are many.
- **IMPORT-HINT-001 [Confirmed]:** [Scope: Base] [Round: 3] [Revision: 2] [Implementation: Implemented; host and scoped Android verified — see implementation-round-3.md] [Flow: collection, entry] An Entry has at most one Hint. - **DIFF-INIT-001 [Confirmed]:** [Scope: Additional] [Round: Undecided] [Flow: review] A new direction-specific Piko Learning Difficulty begins as Unknown. Incomplete rounds can only raise an established value; exact first-incomplete-round handling follows the saturation rule.


## Learning statistics — confirmed 2026-10-13 (supersedes conflicting legacy defaults)

- **STATS-005 [Confirmed]:** [Scope: Additional] [Round: Undecided] [Flow: review] The Daily Average is calculated using **only active learning days** in the reporting window. A day with no qualifying learning activity is excluded from the divisor; a day with qualifying activity counts once. The metric is based on regular Long-term reviews, not Speed attempts or retries. A window with no active days shows no average rather than dividing by zero.
- **STATS-006 [Confirmed]:** [Scope: Additional] [Round: Undecided] [Flow: review] A Learning Streak day qualifies when the user completes **at least one regular Long-term review** during that learning day. Short-term retries and Speed Learning alone do not qualify.
- **STATS-007 [Confirmed]:** [Scope: Additional] [Round: Undecided] [Flow: review] Learning days follow the established local 04:00-to-04:00 boundary, including for Daily Average and Learning Streak. Streaks count consecutive qualifying learning days; the current still-open learning day does not break the streak before it ends.
- **PARAM-STAT-001 [Confirmed]:** [Scope: Additional] [Round: Undecided] [Flow: review, settings] `stats.streakMinimumReviews` defaults to `1` and is available in Developer Settings; the counting unit is regular Long-term reviews per learning day.
- **PARAM-STAT-002 [Proposed]:** [Scope: Additional] [Round: Undecided] [Flow: review, settings] `stats.dailyAverageWindowDays` defaults to `30` calendar days as the lookback window; only active days inside that window form the average divisor. The 30-day window is not yet user-confirmed.

**Examples:** 60 regular Long-term reviews across 3 active days in a 30-day window yields a Daily Average of 20 reviews/active day, not 2 reviews/calendar day. One regular Long-term review qualifies a day for the streak; ten Speed reviews without a regular Long-term review do not.

## Minigame Break — confirmed decisions

- **SPEED-010 [Confirmed]:** [Scope: Additional] [Round: 2] [Revision: 3] [Implementation: Implemented; host and scoped Android verified — see implementation-round-3.md] [Flow: review] For N>1, insert exactly one number Minigame Break at the end of a completed pass when the pool is too small under SPEED-007, unfinished words remain, and none is waiting for its first answered attempt in this round. An empty waiting queue alone is insufficient: newly refilled pool slots may still contain unseen words. In that case proceed to the next complete pass without a game, retaining rotation order. Do not interrupt a pass, add games between its words, or show a game after all words are completed.
