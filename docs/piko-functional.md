# Piko — Functional Specification

**Version:** 0.4.3 · **Updated:** 2026-10-13

This file is authoritative for behavior, data, validation, state transitions and algorithms. `piko-ux.md` is authoritative for presentation and interaction. Requirement IDs cross-reference the two documents. Earlier requirements remain traceable by their stable IDs. Newer explicit decisions supersede conflicting earlier statements; superseded rules are identified below. Presentation details are governed by the UX specification. ## Proposed scope classification — for owner review

### Release assignment and delta process

Release is an independent axis: First (explicitly accepted for first release), Later (deferred), Undecided (assignment open), Superseded (obsolete/resolved decision). All functional IDs now carry a tag. Hints and their dependent requirements are Later by owner decision; other assignments remain Undecided until reviewed individually. Mixed requirements mentioning Hints are deferred as a whole for now and require splitting before their basic portion can be assigned First. Missing UX tags display as Undecided. Base or Minimum never automatically means First. The accepted visible flow is not yet an exhaustive first-release requirement list.

For a release-scope delta, change the tag on the original requirement, preserve its ID, record old/new assignment and reason in DECISIONS.md, review dependencies including conditional Base constraints, and update affected planning and mockup together. No duplicated list, release date, or numbered milestone is introduced.

Every requirement ID below has one proposed scope label. The labels organize implementation priority; they do not change the requirement text, stable IDs, or existing Confirmed / Proposed / Open / Superseded status. A confirmed capability may be Additional and remain a confirmed product intention without being required for the first useful version. An open decision stays open regardless of its scope label. No first-version scope, release date, or implementation milestone has been accepted through this classification.

| Scope label | Meaning | Requirement / decision IDs |
| --- | --- | --- |
| Base | Foundational correctness, data integrity, privacy, validation, and consistency constraints. For an optional capability, its Base constraints become mandatory only if that capability is included; they do not pull the capability into the minimum scope. | 46 |
| Minimum | Proposed smallest useful flow: create a Collection, manually add/manage entries, save locally, and complete basic Long-term self-assessment learning with understandable feedback. | 44 |
| Additional | Capabilities proposed for deferral from that smallest flow, including richer entry UX, categories/grouping, AI, import, Speed/minigames, typed answers, personal Difficulty, advanced preferences, statistics, and developer controls. | 124 |

**Total:** 214 labeled requirement and decision IDs. Topic order is retained so cross-references remain easy to follow; use the labels to distinguish the three scopes.

### Flow associations

Inline `[Flow: collection]`, `[Flow: entry]`, `[Flow: review]`, and `[Flow: settings]` tags connect requirements to creating/opening Collections, manual vocabulary entry, self-assessment review, and basic settings. Multiple associations use one comma-separated tag. Tags identify a topic association, including its optional extensions and conditional constraints; they do not change scope, confirmation status, or implementation completeness. Filter Flow together with Scope: `review` includes Additional review features, while `review` + `Minimum` shows only the proposed Minimum review requirements. Shared privacy, data, and localization constraints remain applicable to every associated flow. The accepted direction for this mockup pass is the visible Minimum flow; individual open functional decisions remain open.

### Boundary decisions still requiring owner agreement

- Is a basic Long-term self-assessment loop useful without Speed Learning, Typed Answer, category management, import, or AI? This classification proposes that boundary; it has not been accepted.
- Offline manual saving is Minimum. Cross-device synchronization is Additional, but no-data-loss and conflict rules are Base if sync is implemented. OFFLINE-003 is Additional because it combines sync states; a minimum offline implementation still needs honest save/error feedback.
- English and German UI support is proposed as Minimum because it is already confirmed for the initial UI. Localizable text architecture is Base; exact German wording remains proposed.
- Hints and Example Pairs are Additional as capabilities. Example language pairing and Hint-default non-retroactivity remain Base constraints if those capabilities ship.
- Undo/previous-grade correction is Additional as a capability; review-history consistency is Base if correction is offered. ENTRY-009 deletion with undo is proposed as Minimum for basic entry management.
- Personal Piko Learning Difficulty and research-oriented incorrect-answer retention are Additional. FSRS-relevant review retention and data minimization are Base. If a feature collects extra data, its privacy purpose and retention must be decided first.
- Labels apply to an entire requirement. Mixed requirements such as CARD-001 (Self Assessment and Typed Answer), ENTRY-001 (focused stack presentation), and PREF-005 (default and expanded direction options) cannot be partially implemented and claimed complete: the minimum flow uses the simple portion, while the full requirement remains pending until all its accepted behavior is present.
- LEARN-005 and OPEN-FSRS-002 are provisionally Minimum for understandable status labels; Mastered controls and their entry/exit rules are Additional. Final status thresholds and the initial status subset need agreement.

The four unnumbered Future / deferred ideas below are all Additional; no new requirement IDs are created for unconfirmed ideas. The experimental parameter table belongs to the Additional developer-parameter capability, while any implemented learning algorithm still needs explicit, validated parameters.

## New and clarified functional requirements

- **VOCAB-EDIT-002 [Confirmed]:** [Scope: Minimum] [Release: First] [Flow: collection, entry] Inline Collection Detail editing retains the vocabulary pair as it was when that editor was opened. After a change, offer Finish editing and Discard changes separately: Finish keeps valid auto-saved edits and closes; Discard restores both original values and closes, including after incomplete input. Invalid or duplicate input blocks Finish. Discard must not create a duplicate or change learning progress. Auto-save remains reversible within this open inline edit session; ENTRY-005's entry-stack behavior is unchanged.
  - The repository captures the exact stored opening pair before editing becomes available. Discard waits for accepted autosaves, restores only that existing entry's texts and comparison keys atomically, and preserves identity, ordering and both directional learning records. A failed rollback retains the snapshot and input for retry; a deleted entry is not recreated. The functional capture/rollback boundary is implemented; the separate visible Discard control is tracked by UX-COLL-012.

- **REVIEW-003 [Confirmed]:** [Scope: Minimum] [Release: First] [Flow: review] When a review session ends, show a dismissible summary popup with the number of vocabulary items learned/completed and the number correct on the first try. Closing returns to the Collection beneath the popup; do not require a separate Back to Collection action. This does not replace existing learning-history or retry-accounting rules. The actual route now opens the immutable final per-launch counters only after captured regular work is exhausted and no retry obligation remains; no-due, voluntary Exit, pending writes, correction and failed selection do not manufacture completion. Safe summary dismissal drains/stops that exact session and returns to its Collection. One real-route completion case plus the eight English/German 320px/200% popup cases verify exact completed/first-try values, no return CTA, X/Escape/backdrop/system-Back dismissal and focus restoration. Two passing English/German Android real-runtime flows additionally reach the actual summary after regular correction and retry completion, assert exact 2 completed / 1 first-try accessible metrics, dismiss to the underlying Collection and retain the resulting state across file reopen. Broader release gates remain separate.

- **COLL-017 [Confirmed]:** [Scope: Minimum] [Release: First] [Flow: collection] A new Collection's required name is prefilled with its selected target language in the interface language (e.g. Korean/Koreanisch). Changing target language updates that default only until the user customizes or clears it. Any explicit name edit stops automatic replacement for that draft, including retyping the original default; clearing does not re-enable it. Changing the native language never renames the draft. A locale-only change preserves draft text, selection and focus under I18N-002; a later target-language change uses the current interface language if the name is still automatic. Empty names remain invalid; multiple Collections with the same language pair or name are allowed.
- **VOCAB-TRASH-001 [Confirmed]:** [Scope: Additional] [Release: Later] [Flow: collection, entry] A future vocabulary trash/recovery area retains deleted entries temporarily. Retention duration, recovery behavior and storage/privacy implications remain undecided; do not infer a duration from the prototype Undo timeout.

- **VOCAB-EDIT-001 [Confirmed]:** [Scope: Minimum] [Release: First] [Flow: collection, entry] Existing vocabulary can be edited directly within its expanded Collection Detail card. Valid changes to the two required language texts save automatically; incomplete or duplicate drafts must not replace the last valid stored pair. Adding vocabulary remains a separate entry-session action.
  The standalone InlineVocabularyEditController establishes the existing-entry autosave boundary without altering ENTRY-005. Stable UUID/owner, immutable raw draft snapshots, last committed pair and revision-aware errors are separate state. One worker serializes writes and coalesces the latest waiting valid pair; later invalid input stays raw while previously accepted valid snapshots may finish without clearing its validation. Repository transactions update both texts/keys together and leave directional learning state unchanged. Current duplicate/storage failures retain raw input and last committed values, with single-flight retry; stale failures cannot overwrite newer validation. Canonical-equivalent raw spaces/decomposition remain in the buffer but are not reported as unpersisted changes after draining. Ordinary typing stays available during autosave. Disposal rejects new work and clears exposed editing state; accepted writes can drain without late notifications before caller-owned storage closes. This is controller-layer evidence only: actual inline expansion, compact fields, finish/discard and Android integration retain their own pending requirements.

- **MATCH-001 [Confirmed]:** [Scope: Base] [Release: Undecided] [Flow: review] Typed answers may be submitted empty and are then treated as an answer attempt; the learner retains final authority over the Correct/Incorrect grade.
- **MATCH-002 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] Typed answer matching detects character-level near matches and accepted language-specific orthographic variants. Similarity is a suggestion, not an automatic semantic synonym acceptance rule.
- **MATCH-003 [Confirmed]:** [Scope: Base] [Release: Undecided] [Flow: review] A different meaning or wrong synonym is not automatically accepted as correct; the learner can override the suggested grade.
- **MATCH-004 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] Submitted incorrect typed answers are retained as learning events for potential future error-pattern analysis, separately from the final learner-confirmed grade.
- **SPEED-RESET-001 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] Completing Speed Learning without an incorrect answer leaves an existing direction-specific FSRS state unchanged.
- **SPEED-RESET-002 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] Completing Speed Learning after at least one incorrect answer restarts the corresponding direction's long-term learning state from its initial learning stage. Exact FSRS state initialization is to be specified with the scheduler integration.
- **SPEED-RESET-003 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] The user can explicitly reset the learning progress of a Learning Item; resetting one direction does not silently reset the other.
- **SPEED-ELIG-001 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] A long lapse alone does not automatically reset a Learning Item or force it into Speed Learning; users may deliberately select long-unreviewed items for Speed refresh.
- **SPEED-ELIG-002 [Open]:** [Scope: Additional] [Release: Undecided] [Flow: review] Define evidence-based automatic Speed recommendation for repeated failures under FSRS without introducing artificial phase regressions.
- **UNDO-001 [Confirmed]:** [Scope: Base] [Release: First] [Flow: review] Correcting the immediately previous grade replaces the corresponding review event and consistently recalculates its FSRS state and retry scheduling rather than creating a second review. The atomic scoped transaction reuses the regular event UUID and original UTC review instant, recalculates from the receipt's exact prior FSRS card, advances only card/scope revisions while leaving the answer ordinal unchanged, and replaces/removes/restores the current-round retry without extending its original learning-day expiry. Retry-answer correction never writes FSRS or regular history. Exact latest receipt, authoritative item/scope state and any post-answer wait-mutation chain are optimistic guards; stale, forged, concurrent or non-latest correction fails without a partial write. Twenty-seven real-SQLite cases cover all 3×3 regular and retry rating transitions, wait chains, expiry, rollback/retry, concurrency and unrelated-scope preservation. Two passing Android real-runtime flows additionally replace Hard with Good using the same event UUID/original UTC instant in opposite directions and retain the corrected state across file reopen; the exhaustive transition matrix remains host evidence. Broader release gates remain separate.
- **EXAMPLE-005 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: entry, review] All Example Pairs of an Entry remain available on its Learning Card, including when there are many.
- **IMPORT-HINT-001 [Confirmed]:** [Scope: Base] [Release: Later] [Flow: collection, entry] An Entry has at most one Hint; a conflicting imported Hint is proposed for explicit review, while the existing Hint remains unchanged unless the user explicitly accepts replacement.
- **DIFF-INIT-001 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] A new direction-specific Piko Learning Difficulty begins as Unknown. The first completed round initializes it from the retry score (0 for first-try correct); subsequent completed rounds use EMA weight 0.40. Incomplete rounds can only raise an established value; exact first-incomplete-round handling follows the saturation rule.


## Learning statistics — confirmed 2026-10-13 (supersedes conflicting legacy defaults)

- **STATS-005 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] The Daily Average is calculated using **only active learning days** in the reporting window. A day with no qualifying learning activity is excluded from the divisor; a day with qualifying activity counts once. The metric is based on regular Long-term reviews, not Speed attempts or retries. A window with no active days shows no average rather than dividing by zero.
- **STATS-006 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] A Learning Streak day qualifies when the user completes **at least one regular Long-term review** during that learning day. Short-term retries and Speed Learning alone do not qualify.
- **STATS-007 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] Learning days follow the established local 04:00-to-04:00 boundary, including for Daily Average and Learning Streak. Streaks count consecutive qualifying learning days; the current still-open learning day does not break the streak before it ends.
- **PARAM-STAT-001 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review, settings] `stats.streakMinimumReviews` defaults to `1` and is available in Developer Settings; the counting unit is regular Long-term reviews per learning day.
- **PARAM-STAT-002 [Proposed]:** [Scope: Additional] [Release: Undecided] [Flow: review, settings] `stats.dailyAverageWindowDays` defaults to `30` calendar days as the lookback window; only active days inside that window form the average divisor. The 30-day window is not yet user-confirmed.

**Examples:** 60 regular Long-term reviews across 3 active days in a 30-day window yields a Daily Average of 20 reviews/active day, not 2 reviews/calendar day. One regular Long-term review qualifies a day for the streak; ten Speed reviews without a regular Long-term review do not.

## Collections and languages
- **SETTINGS-001 [Confirmed]** [Scope: Minimum] [Release: First] [Flow: settings] First-release Settings exposes only App Language, offering English and German. Apply the selected interface language immediately and retain it across application restarts. Learning direction is selected in the review flow, not offered as a first-release Settings field. This is an application requirement; the mockup's live language switching does not claim production persistence.
  - The real home opens Settings through its top-right action. One App Language dropdown offers the canonical autonyms English and Deutsch. An app-lifetime controller updates interface copy and Flutter native localization together without replacing the Navigator, runtime storage owner, open raw vocabulary editor or revealed review/Hard state. This never translates or changes stored vocabulary, FSRS, regular history, retry obligations, allocator state or unrelated settings.
  - Runtime bootstrap reads the existing `locale` setting before normal content. Exact retained `en`/`de` wins; missing or unsupported values use English without rewriting the preference. Read failure has an explicit loading-error/retry state, not a fabricated empty home or missing preference. This hydration also applies to an injected controller/initial locale when using `PikoRuntime`; custom non-runtime homes remain independently composable, and injected controllers remain caller-owned.
  - A single admitted selection registers its complete storage drain before optimistic interface change or the write. Repeated or stale confirmation/close callbacks cannot delete twice or pop an unrelated route. Replacement/disposal closes only the owned dialog; a new delete does not start after its owner ends, while already accepted database work may finish without late focus, errors or navigation. Success returns to the overview only when the captured route is current. Host integration is verified. A passing Android real-runtime case additionally confirms explicit Collection deletion and committed cascade across file reopen while an unrelated Collection remains. Final header placement and broader release gates remain separate.

## Vocabulary Entries and examples
- **VOCAB-001 [Confirmed]** [Scope: Base] [Release: First] [Flow: collection, entry] Distinct meanings are stored as separate Vocabulary Entries, even if one language's entry is identical. Each stored Entry has its own UUID, Collection identity and required target/native texts. Sharing either one text does not merge identities or meanings. Local schema 3 establishes this storage boundary; manual entry screens, normalized pair uniqueness and directional learning state remain their own requirements.
- **VOCAB-002 [Confirmed]** [Scope: Base] [Release: First] [Flow: collection, entry] An exact pair of language entries may occur only once within a Collection; attempts to save an exact duplicate are blocked using the VOCAB-012 comparison policy. New and edited texts are saved in canonical display form, with required comparison keys and collection-scoped SQLite uniqueness. Editing an Entry may retain its own pair; invalid or duplicate edits preserve the last valid saved Entry. Schema 4 migration preserves existing IDs, owners, raw display text and insertion order while computing keys; same-Collection normalized collisions abort without deleting or merging Entries. This establishes storage/repository validation; user-facing editor feedback belongs to its screen requirements.
- **VOCAB-003 [Confirmed]** [Scope: Base] [Release: First] [Flow: collection, entry] The same exact vocabulary pair, using VOCAB-012 comparison normalization, may exist in different Collections, including Collections with matching names and language pairs. Each Entry keeps its own identity and owner; editing one does not edit the other. Same-Collection duplicate blocking still applies. Repository acceptance and file-reopen tests verify this boundary; manual-entry presentation remains separate.
- **VOCAB-004 [Confirmed]** [Scope: Additional] [Release: Later] [Flow: entry, review] An entry may have an optional Hint, separate from category assignments.
- **VOCAB-005 [Confirmed]** [Scope: Additional] [Release: Undecided] [Flow: entry, review] An entry may contain any number of Example Pairs, including none; the editor initially exposes space for one optional pair and provides an explicit Add Example action for more.
- **VOCAB-006 [Confirmed]** [Scope: Base] [Release: Undecided] [Flow: entry, review] Each Example Pair contains the sentence and its translation in the two Collection languages.
- **VOCAB-007 [Confirmed]** [Scope: Additional] [Release: Later] [Flow: entry, review] An entry's Hint Visibility is either Always visible or Hidden until tapped during learning.
- **VOCAB-008 [Confirmed]** [Scope: Additional] [Release: Later] [Flow: entry, review, settings] The initial Hint Visibility default is Always visible and is stored globally per user.
- **VOCAB-009 [Confirmed]** [Scope: Additional] [Release: Later] [Flow: entry, review, settings] Users can override Hint Visibility for an individual entry during creation or editing, and can explicitly make that choice the new global default without repeated prompts.
- **VOCAB-010 [Confirmed]** [Scope: Base] [Release: Later] [Flow: entry, review, settings] Changing the global Hint Visibility default affects newly created entries, not existing entries.
- **VOCAB-011 [Confirmed]** [Scope: Additional] [Release: Later] [Flow: entry, review] When a hidden Hint is tapped during a learning question, it becomes visible for the rest of that question and cannot be hidden again; the next presentation starts from the entry's configured visibility.
- **VOCAB-012 [Confirmed]** [Scope: Base] [Release: First] [Flow: collection, entry] Normalize each vocabulary text for display by trimming surrounding Unicode whitespace and applying Unicode NFC, preserving case, punctuation and internal whitespace. Compare pairs using locale-independent Unicode lowercase followed by NFC on that normalized text. Uppercase ẞ and lowercase ß compare equally, while ß and ss remain distinct; do not use full case folding, compatibility normalization, accent removal or spelling-equivalence rules. Empty normalized text remains empty for required-field validation. Reusable pure functions define this policy; repository enforcement and normalized pair uniqueness belong to VOCAB-002.

## Manual Entry Sessions
- **ENTRY-001 [Confirmed]** [Scope: Minimum] [Release: First] [Flow: entry] Manual entry uses a vertically scroll-driven Focused Card Stack; the card moving into focus expands smoothly and adjacent cards appear compactly above/below it, without requiring a tap to focus. The production screen consumes a caller-owned Entry Session controller and Collection metadata, showing only that session's confirmed records and its temporary draft. ## Minimal learning data — confirmed decisions

- **DATA-001 [Confirmed]:** [Scope: Base] [Release: First] [Flow: review] Do not retain a complete event history for every short-term retry attempt. The regular-review recording API requires an explicit regular/reinforcement kind and rejects reinforcement with a typed failure before card validation, FSRS scheduling or database access. Repeated boundary submissions leave existing regular events, complete directional memory and review revision unchanged, including after file reopen. RETRY-006 now verifies the actual route's repeated Incorrect reinforcement and final Hard/Good in both directions: only the first regular event/card/revision remains until the next legitimate ordinary due review. No retry-attempt log or typed-answer retention is introduced. Required current-round error/gap/wait/expiry state, scope answer ordinal and latest in-memory correction receipt are separate from complete event-history retention. Host acceptance is implemented; Android retention verification remains pending.
- **DATA-002 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] Retain the number of retries required for each completed retry round.
- **DATA-003 [Confirmed]:** [Scope: Additional] [Release: Undecided] [Flow: review] Retain submitted incorrect Typed Answers for later error-pattern analysis.
- **DATA-004 [Confirmed]:** [Scope: Base] [Release: First] [Flow: review] Retain regular FSRS-relevant reviews with a stable event UUID, Learning Item owner, exact UTC review time, Again/Hard/Good rating and nonnegative FSRS generation/reset discriminator. New and migrated Learning Items start at generation zero; no reset feature is introduced. A separate nonnegative review revision advances on every accepted regular review, allowing exact-prior checks to reject stale/repeated submissions even when FSRS returns an unchanged card. The production repository loads and validates the expected complete item identity/ownership/direction/version/card/generation/revision, schedules through the pinned adapter and commits the event, complete card and revision in one transaction. Failed writes leave no partial event/state; an immutable in-memory receipt retains exact prior/result and event context for later correction without storing redundant card snapshots. Schema 7 migrates versions 1–6 without rewriting existing cards or inventing past reviews, retaining IDs, vocabulary order/bytes, settings and allocator marks. File reopen retains exact event payloads, per-item order and complete memory/revision. Vocabulary deletion cascades history; eight-second Undo restores its UUIDs/order/generation and complete item state with conflict/transaction guards. Collection cascade refreshes history observers while preserving other Collections. Host storage acceptance is implemented; correction, retry accounting, product review integration and Android acceptance remain pending. Reset behavior is outside the first release.
- **DATA-005 [Confirmed]:** [Scope: Base] [Release: First] [Flow: collection, entry, review, settings] Store only learning data needed for product behavior and specifically intended analysis. First-release logical storage is limited to Collections, vocabulary, independent directional learning state, regular reviews, current retry obligations, scoped answer ordinals, identity/order allocators and the interface locale. Repeated reinforcement errors update current state rather than append attempt history; success removes the current obligation. No typed-answer history or analytics store is introduced. A real file-backed review sequence and exact schema/snapshot reopen test verify this retention boundary. This does not claim physical secure erasure, an operating-system backup policy or completed Android verification.

Active retry rounds retain the current retry count and expiry/day-boundary state; after completion or expiry they may be summarized. A timestamp for every short-term retry is not required. A timestamp on an incorrect Typed Answer remains optional unless time-based error analysis is approved. These rules refine MATCH-004 without requiring a full retry event log.
